# 導讀方法論：各區塊寫法要領

> 本方法論已在實際 Unity 專案的 UI 管理單檔上實戰驗證。核心思想：**裸讀是「邊挖隧道邊畫地圖」，導讀是「先給地圖再進隧道」**——工程師裸讀時 80% 時間花在搞清楚什麼值得讀，地圖把這 80% 做掉，讓精讀時間花在真正值得精讀的 20%。

## 定位：導讀是什麼、不是什麼

- **是鷹架，不是建築**：心智模型終究要在讀者腦中建起來，地圖只改變理解的經濟學。讀者熟了系統，地圖即棄；程式碼改版，地圖重產。
- **是假設清單，不是真理**：地圖上每個論斷都掛行號錨點，讀者 trace 時逐一對質。讀者與地圖的關係是法官與證人。
- **不是 API 文件**：不求覆蓋全部 public 成員，只求最短路徑建立心智模型。

## 區塊 1：一句話心智模型

解決「不知道從哪開始」。第一句必須讓讀者能轉述：「X 是負責 Y 的 Z」。第二件必說的事是**複雜度來源**——這個檔難讀的原因（狀態多？時序敏感？歷史包袱？），讓讀者預期該把注意力放哪。

- 寫法：2~4 句敘述，禁止寫成條列。
- 自查：遮住目標名稱，這段話是否仍只可能描述這一個系統？太泛 = 重寫。

## 區塊 2：資料模型先行

解決「方法在改什麼看不懂」。人腦理解行為（方法）前必須先有狀態（欄位）的掛載點——同樣資訊倒過來給，效果差一個量級。這是**順序設計**：狀態表先給，後面每個方法讀者都能掛上「它在改哪幾個狀態」。

- 只收「核心狀態」：去掉純轉發、純 UI 引用的欄位；一張表 ≤ 12 列，超過代表該拆導讀。
- 「角色」欄一句話寫**它代表什麼狀態**，不是型別翻譯（❌「面板的列表」→ ✅「目前開啟中面板的堆疊順序，排序的 source of truth」）。
- 用途定位：這張表是讀者 trace 時的隨身查表，不是先背完才能動。

## 區塊 3：入口與主流程

解決「呼叫鏈迷路」與「找不到入口」。程式碼的物理排列（方法在檔案裡的順序）與邏輯結構（誰呼叫誰）通常不一致；按對外行為動詞重組，給的是使用者視角的入口清單。

每個動詞組**強制三件事**（資深工程師接手任何系統手動做的第一步，原樣固化）：

1. **進入點**：方法簽名 + 行號錨點
2. **觸發來源**：誰呼叫、何時觸發。現代框架的入口常常靜態讀不出來（反射呼叫的熱更入口、prefab/序列化回呼、幀驅動、事件掛載、DI 容器）——這是導讀最值錢的部分，必須寫明
3. **核心參數表**：參數、型別、用途一句話

然後才列呼叫鏈。呼叫鏈只列「站點」（每站附錨點），不貼程式碼。

- 動詞分組以**對外行為**為單位（開/關/插隊/重排），不是以方法為單位；一個動詞可能橫跨多個方法。
- 動詞數量 3~7 個為宜，超過代表目標太大，回 Step 1 建議拆。

## 區塊 4：不變量

解決「逐行讀演算法的低效」。資深讀者不需要排序/快取淘汰的逐行解釋，只需要「這段維持什麼性質」（如：任何時刻渲染深度與開啟堆疊順序一致）。知道不變量後，逐行讀是**驗證**，不是理解——驗證比理解快一個量級。

- 每個演算法一行：錨點 + 不變量一句話。
- 禁止寫實作流水帳（「先 for 迴圈、再 swap、最後 return」= 違規）。
- 找不變量的口訣：這段碼跑完，什麼條件永遠成立？破壞這條件會出什麼 bug？

## 區塊 5：輔助層 / 支線

解決「分不清骨幹和血肉」。成熟檔案 40% 以上行數是快取、防禦、優化碼，對建立心智模型貢獻接近零——但**stale 容忍分界線本身是該系統最值錢的設計決策**，必須標出：誰必須用新鮮資料、誰可容忍 stale。

- 「第一遍可跳過？」欄是給讀者的明確授權，讓他放心略過支線。
- 防禦碼若對應已知坑（知識庫有記錄），引用來源。

## 區塊 6：閱讀順序清單

前五區是地圖，這區是路線。每列 = 一段可一次讀完的範圍（方法 / 區段），標「精讀 / 掃過」+ 預估分鐘。

- 時間預估的目的：讓讀者能排程（「這系統我需要 90 分鐘」），消除面對未知工作量的焦慮。
- 順序原則：先資料模型宣告區 → 主動詞入口 → 不變量演算法（精讀）→ 支線（掃過）。
- 親手 trace 的建議寫在這：哪幾條鏈值得開 IDE 逐步追，哪幾條看地圖摘要即可。

## 區塊 7：實機觀察入口

靜態讀碼建的模型是假設，邊跑邊看才變確信。很多行為（執行順序、生命週期、熱更時序）靜態讀根本看不出來。

依專案技術棧列出可用手段（**查專案 CLAUDE.md / 知識庫確認專案自建的 debug 工具**）：

- Unity：Inspector 指名哪個物件哪個元件欄位、unity-mcp（Play Mode / read_console）、專案自建 debug bridge
- 通用：log 關鍵字（指名 grep 什麼）、debugger 中斷點建議位置、監控/統計出口（唯讀 property、/monitor 端點）

## 區塊 8：文件時效警告

防止被舊文件帶偏。知識庫常落後原始碼（搬遷、重構後尤甚），新人最容易踩的坑是信了過時文件。

- Step 0 標「需驗證」的來源，在 Step 2 對質後的結論寫這裡：哪份文件哪一節已過時、以哪個原始碼段落為準（附錨點）。
- 每跑一次導讀 = 對知識庫做一次時效稽核；發現的過時點建議使用者更新知識庫（只建議，不自行改）。
- 無矛盾也要明寫「本次未發現」，讓讀者知道稽核做過了。
